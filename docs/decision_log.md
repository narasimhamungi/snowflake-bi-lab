# Decision log

Format: decision — reason — what it costs.

1. **Snowflake, not BigQuery.** The target advert names Snowflake. BigQuery's sandbox is the fallback if the trial is unavailable; only the platform actually used may be claimed. *Cost:* trial expires, so the repo's evidence is code, screenshots and a PDF, not a live dashboard.
2. **Power BI Desktop in Import mode.** Free, Windows-native, and the data volume (~0.7M consensus rows) is small. DirectQuery would need a live warehouse for every viewer and a running trial. *Cost:* the report is a snapshot.
3. **Full refresh (TRUNCATE + COPY), not MERGE.** The export is a complete snapshot of a small table set; refreshing it wholesale is idempotent and simpler to prove correct. MERGE earns its keep for incremental sources, which this is not. *Cost:* does not demonstrate incremental loading; do not claim it.
4. **`sources_available` flattened to a pipe-delimited string** (Postgres `TEXT[]`). Loading Parquet LIST into a Snowflake ARRAY is behaviour not verified here and nothing downstream needs the array. Membership is exposed as `has_yfinance` / `has_tiingo`. *Cost:* RAW is not byte-for-byte 1:1 with Postgres; this is the only deviation.
5. **No PRIMARY/FOREIGN KEY constraints in RAW.** Snowflake does not enforce them; declaring them would document a guarantee the engine does not give. The DQ checks enforce uniqueness and referential integrity instead.
6. **Exact decimals end to end.** `NUMERIC(18,6)` → `decimal128(18,6)` → `NUMBER(18,6)`. No floats until a metric is computed (returns/vol are explicitly cast to DOUBLE).
7. **Fingerprints over bare row counts.** Row counts miss precision loss, type coercion and silently altered values; sums and min/max keys catch them. Expressions are portable SQL so Postgres, Snowflake and DuckDB give identical answers.
8. **Recompute reconciliation instead of only loading the report.** The lakehouse report is a text artefact; the warehouse recomputes the comparison from per-source rows and then compares *that* to the report's published numbers (control check). It must be the report for the same ingest date as the gold build.
9. **Hand-written SQL checks, no dbt.** Keeps the first version to the tools the advert names and keeps every statement explainable. dbt Core (models + tests + lineage docs) is the more standard way to do this and is the obvious next upgrade; it was not done. Check `dbt-snowflake` support for your Python version before adding it.
10. **DuckDB as the test engine.** Lets the exact production SQL files run in CI without a Snowflake account. *Cost:* DuckDB accepting a statement is not proof Snowflake does. Listed under "Unverified".
11. **Severity levels.** OHLC ordering and coverage rules are `warn` (real properties of vendor data, e.g. the HUBB bad print the lakehouse tolerates); integrity rules are `error`.
12. **Gap returns.** A return spanning more than 5 calendar days is kept but excluded from rolling volatility and sector averages; otherwise a missing data stretch looks like one large move. Rolling vol needs a full 21-observation window.
13. **Equal-weighted sector return** over whichever securities have a non-gap return that day. The member set varies with coverage: a barometer, not an index.
14. **No market data committed.** Parquet exports are git-ignored. The prices originate from Yahoo (via yfinance) and Tiingo; redistributing them in a public repo is a licensing question this project does not take on. Screenshots/PDF show aggregates only; check that no per-row vendor data is displayed at length.
15. **Warehouse sizing.** XSMALL, auto-suspend 60 s. No performance or tuning claims: the data is too small for them to mean anything.
16. **NaN in NUMERIC columns becomes NULL on export.** The lakehouse loader casts the eight price fields with an unguarded `float()` (volume is guarded), so a missing vendor value is stored in Postgres NUMERIC as `NaN`. Snowflake NUMBER cannot hold NaN, and pyarrow rejects it as a decimal. The export maps NaN to NULL (a constrained `NUMERIC(p,s)` cannot hold Infinity, so NaN is the only non-finite case), records the per-column count in `manifest.json` and prints it, and every fingerprint includes a per-column NULL count so a load that drops or invents NULLs is caught. `null_price_fields` (warn) shows the affected row count in `mart.dq_results`. *Cost:* the warehouse cannot distinguish "vendor sent NaN" from "vendor sent nothing". The source-side fix is a `NULL` guard in the lakehouse loader, which this repo does not change.
